## How entries are structured

Every API entry uses the same sections, in this order:

| Section | Content |
| --- | --- |
| Overview | The lead paragraph: what the API is for, in one or two sentences. |
| Signature | The declaration, copied verbatim from the referenced source file. |
| Parameters | One row per parameter: name, type, optional, meaning. |
| Return value | Type and meaning of the result. |
| Behavior | Documented behavior, each statement backed by the source or the official guides. |
| Code example | A minimal example, taken from the official guides or the source documentation. |
| Related APIs | Links to related entries and guide sections. |
| Source reference | Permalink to the exact source location at a tagged release. |

## Verification

An entry is marked **verified** only when its signature was checked against a specific published version of the
`elysia` package and it links to the exact source location. Everything else is marked **unverified**. Imported guide
content is never marked as verified automatically, and no signature or behavior is added unless it appears in the
source code or the official documentation.

Contributors can start from `src/content/docs/reference/_template.mdx`, which is not published.
